# AGENTS.md — app-platform

**app-platform** (working name) is a single-tenant platform for building small automation apps (scheduled jobs, workflows, internal tools) on a shared core: identity, sessions, permissions, audit, jobs, cross-app data and a server-driven UI. Apps are written by hand or generated by the in-platform App Studio.

## How to use the docs (read this first)

Context is limited. Do not read `docs/` wholesale.

1. Open `docs/README.md`. It lists every doc with one line on what it covers and when to read it.
2. Read only the docs whose "read when" matches your task. Most tasks need 1 to 3 files.
3. Each folder you work in may have its own `AGENTS.md` with local rules. It applies on top of this file.
4. Decisions live in `docs/decisions/` (ADRs). Do not reverse one silently: propose a new ADR (skill `write-adr`).
5. For a recurring task, check `.claude/skills/` first; a skill gives the exact steps.

## Golden rules

- **Dependency rule:** domain <- application <- adapters / interfaces. Domain imports nothing. Application defines ports (interfaces); adapters implement them. Only `services/server` (the composition root) wires concrete adapters. `pnpm depcruise` enforces this.
- **No framework owns the code.** Fastify, Drizzle, Better Auth, Graphile Worker and json-render are adapters behind ports.
- **Apps never touch each other's tables.** Read via exported views, write via exported commands, react via events. Everything through the SDK `ctx`.
- **Every state change is authorised and audited in the same transaction** (`ctx.authorize`, `ctx.audit`).
- **One deployment = one organisation.** No tenant ids. Isolation comes from app instances (one Postgres schema each) and instance-scoped permissions.
- **UI is server-driven.** Pages are YAML specs validated by JSON Schema, compiled to JSON, rendered from the `@platform/ui` catalog. Do not hand-write app pages in React unless adding a catalog component.
- **API contracts are `.proto` files** (Connect RPC). Change the contract first, then `buf generate`.
- DRY, SOLID, small functions, constructor injection. No decorators or reflection-based DI.
- Keep resource use low: the target is one 2 vCPU / 4 GB VPS.

## Commands

| Task | Command |
| --- | --- |
| Start everything | `pnpm dev` |
| Full check (what CI runs) | `pnpm check` |
| Typecheck | `pnpm typecheck` |
| Lint and format | `pnpm lint` / `pnpm format` |
| Architecture rules | `pnpm depcruise` |
| Tests | `pnpm test` (unit), `pnpm test:int` (Postgres), `pnpm test:e2e` |
| API contracts | `pnpm buf:lint`, `pnpm buf:breaking`, `pnpm buf:generate` |
| Validate page specs | `pnpm spec:check` |
| DB migrations | `pnpm db:generate`, `pnpm db:migrate` |

Run `pnpm check` before saying a task is done.

## Repository map

| Path | What lives there |
| --- | --- |
| `packages/core-domain` | Entities, value objects, domain events. Zero dependencies |
| `packages/core-application` | Use cases and ports |
| `packages/adapters/*` | Port implementations (Postgres, auth, queue, sandbox, mail, LLM) |
| `packages/interfaces/*` | Driving adapters: Connect RPC, webhooks, CLI |
| `packages/sdk` | The `ctx` contract apps code against |
| `packages/ui` | `@platform/ui` components, layouts, catalog |
| `proto/` | `.proto` contracts |
| `modules/<id>` | Supporting modules apps plug in (contacts, record timeline, ...) |
| `apps/<app>` | One app per folder, same layering as the core |
| `services/server` | Composition root and process entry |
| `services/web` | Static React shell |
| `docs/` | Knowledge base (start at `docs/README.md`) |

## Working agreements

- Work inside the Dev Container (`docs/guides/dev-environment.md`); never install project tools on the host.
- [Conventional Commits](https://www.conventionalcommits.org/) for every commit and PR title; [SemVer](https://semver.org/) for every version. Breaking changes use `!` and a `BREAKING CHANGE:` footer. Details: `docs/guides/versioning.md`.
- Small PRs, one concern each, squash-merged.
- Tests first for use cases and ports (contract tests for every adapter).
- If you change behaviour described in `docs/`, update that doc in the same PR (skill `update-docs`).
- Never put secrets in code, docs, tests or logs.
